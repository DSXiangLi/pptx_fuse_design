# demo1 框架对比分析：对方（omelette 系）vs 我们（html-pptx）

> 日期：2026-09-20 · 方法：读实现代码（`方向B 极黑冷调.html` 1568 行全文 + `方向A 暖米编辑.html` 结构 + `image_slot.js` 641 行全文），不读 README 下结论。
> 命名：从 `image_slot.js` 的宿主桥接（`window.omelette.writeFile`）与注释（design_canvas.jsx / deck_stage / PPTX export）推断，对方是某 agent 运行时的设计-交付框架，下称 **omelette 系**。

## 一、架构画像

| 维度 | omelette 系 | 我们（html-pptx） |
|---|---|---|
| 产物形态 | 长滚动多屏落地页（max-width 1440 + clamp 流式字号 + 断点 1100/640） | 16:9 固定画布分页 + transform 缩放 + 竖向 snap |
| 布局哲学 | 流式响应式（移动端重排） | 固定画布保真（打印/演示/编辑坐标系稳定） |
| 主题机制 | **一方向一文件**：方向A/方向B 两个独立手工整页 HTML，零共享层 | 主题 = 七层表达力栈（token + 主题 CSS 槽位），20 主题 × 变体 + 两两分化机器门槛 |
| 字体策略 | Google Fonts CDN（联网依赖，Bebas/Inter/JetBrains Mono） | 系统栈离线优先 + G2 可选联网备选 |
| 动效架构 | 13 组 bespoke IIFE（每效果一段自写 JS） | 8 族 41 recipe 词汇表 + 注意力预算 + 五层矩阵 + 主题签名 |
| 图片系统 | **`<image-slot>` Web Component**（Shadow DOM）：拖拽/点击上传 + sidecar JSON 持久化（宿主桥接写文件）+ **双击 reframe 裁剪**（平移/角点缩放/滚轮缩放，指针捕获） | 契约三属性（slot/intent/state）+ 编辑器 FSAA 写回 assets/ + AI 插画管线 |
| 编辑与持久化 | 无就地文字编辑；图片状态存 `.image-slots.state.json` 伴生文件（HTML 不变，状态外挂） | 编辑器就地改字改图，序列化净化**写回 HTML 本身**（文件即真相） |
| 质量保障 | 无测试、无校验器、无契约——质量靠单 agent 审美与自查 | 46 项 harness + sync-themes/check-images 校验器 + 编辑契约 |
| 交付定位 | **设计参考稿**：README 明示"在 React/Vue 重新实现"，HTML 不是交付物 | HTML 即交付物（可演示可编辑可保存） |
| 导出 | 有 PPTX 导出链路（image_slot.js 注释证据） | 明确不做反向导出（交付物即 HTML；compat-roadmap 留规划） |

## 二、收敛同构（双方独立得出的相同结论——互相印证）

1. **运行时拆字**：对方 shatter/split-char 也是运行时拆 span（`ht-char`/`split-char`），完成后靠 class 归位——与我们"文本破坏性动效必须运行时化"同构；
2. **语义页标注**：对方 `data-screen-label="01 封面"` ≈ 我们 `data-chapter`；
3. **IO in-view 生命周期 + rAF 节流 + reduced-motion 兜底 + CSS var token**——双方动效基础设施同构；
4. **图片槽位概念**：双方独立发明了"槽位"——他们是组件（`<image-slot>`），我们是契约（`data-image-slot` 三属性）；
5. **同内容多方向对照**：方向A/方向B 两个手工文件 ≈ 我们的撞脸矩阵（20 主题同内容样张）与 J 期同题三 deck。

## 三、真正值得学的（对方的强项）

1. **reframe 裁剪编辑**（image_slot.js 的最大亮点）：双击进裁剪模式——图溢出槽位的半透明鬼影 + 四角手柄等比缩放（对角锚定）+ 拖拽平移 + 滚轮缩放 + Esc/外点提交。我们的图片替换只换不裁。**行动项**：编辑器图片 reframe 列入规划（工程量大：指针捕获 + frame-% 坐标系 + 净化/保存口径，放 compat 评估后排期）。
2. **sidecar 状态外挂**（`.state.json`）：HTML 不变、状态在外——分享链接场景下 HTML 保持原版、每个人看到同一份用户图。我们"文件即真相"在单文件交付更强，但**嵌入态**下 sidecar 模式值得记住（宿主存状态、产物不动）。
3. **hover 整卡反色**（pain-card hover → accent 底黑字整卡反转）：内容卡片的强交互反馈。我们的 ptr 族是 tracker 系（tilt/magnetic/spotlight），缺"hover 状态反转"这种纯 CSS 微交互词汇——**行动项**：motion.md ptr/交互层补 hover 反色纪律（容器级、仅可交互暗示处、accent 预算内）。
4. **流式断点**是落地页形态的正确选择——不适用于我们的 16:9 画布决策，但确认了"嵌入窄口"场景的边界：画布缩放极小字号时退化（未来可评估阅读模式，非本期）。

## 四、我们的护城河（对方没有或明显弱）

1. **可编辑性**：对方产物改字只能重新生成；我们的就地编辑 + 契约 + 净化保存是整条差异化主轴；
2. **主题规模化**：对方换方向 = 手工整页重写（质量上限高、不可规模化）；我们 20 主题 × 变体 + 七层 + 机器门槛——且 I 期证明新主题构思已流程化（世界采样六步）；
3. **质量保障体系**：harness/校验器/契约三层 vs 对方零测试；
4. **动效纪律**：对方 13 组动效无预算概念（靠单个作者自控），我们的注意力预算/五层矩阵/主题签名可机器校验；
5. **离线自足**：对方依赖 Google Fonts CDN 与宿主桥接；我们零依赖单文件。

## 五、结论

两个框架回答的是不同问题：omelette 系回答"**设计稿怎么美**"（单点极致、手工定制、交给开发重写），我们回答"**HTML PPT 怎么既能生成又能编辑还能交付**"（系统化、契约化、可规模化）。视觉层我们该学的已在 K 期学完（密度/动效/字体三层解剖）；工程层这次新增的清单只有两条：reframe 裁剪（编辑器未来项）与 hover 反色微交互（motion 小项）。sidecar 模式记为嵌入态备选思路。
