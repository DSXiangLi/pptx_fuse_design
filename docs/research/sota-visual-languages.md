# SOTA 视觉语言：可衍生性判定与枚举规范

> 定位：回答一个元问题——SOTA 级视觉能不能靠原则让 AI 自主衍生？结论是不能全衍生，必须枚举的部分给出"枚举项法定结构 + 入库验收标准"，保证枚举可扩展。
> 索引：`source-survey.md` · 综合判断：`optimal-solution.md` · 日期：2026-09-17。

## 1. 核心问题与判定

**问题**：如果五条第一性原则足够强，AI 能不能在原则约束下自己长出 SOTA 级视觉，从而主题库、组件库都可以不要？

**判定：分层回答，不能一概而论。**

- **排版结构层——可以衍生。** 字阶、字重阶梯、行高、槽位容量、密度档、留白节奏，这些都有数学性不变量（比如"同页小字字重必须 ≥ 大字字重"、"1 行标题 ≤8 字取 6.4vw 档"）。原则 + 渲染测量闭环足以让 AI 在这一层收敛到高分。这一层**枚举是多余的**，写原则即可。
- **视觉身份层——不可纯衍生。** 配色组合、字体配对、材质气质（editorial / swiss / brutalist / 终端美学……）是**文化性知识**：一组配色"高级"没有函数可算，只有策展共识。AI 的训练分布决定了它自由发挥时必然收敛到均值审美（紫蓝渐变、居中 hero、卡片墙——见 `source-survey.md` 问题 1）。这一层**枚举是唯一的解**。
- **证据**：六家参考项目中，所有达到 SOTA 观感的，身份层无一例外是枚举——guizang 锁死两套风格、frontend-slides 策展 12 预设 + 34 套 bold 模板、codex 12 套风格库、dashi 12 主题。没有任何一家靠"原则 + 自由发挥"做出过稳定的高级感。（各项目细节见 `projects/`。）

**判定结论**：SOTA 视觉 = **可衍生层用原则打底 + 不可衍生层策展枚举**。用户的预判成立：纯原则到不了 SOTA。但枚举必须有纪律，否则就是 dashi 的 1020 个页面模板——枚举下沉到版式层，保护变成枷锁。

## 2. 枚举分层模型

| 层 | 内容 | 策略 | 现状载体 |
|---|---|---|---|
| L0 主题视觉语言 | 色板 + 字体栈 + 材质气质 | **枚举**（只选不改） | `themes.md` 13 套 |
| L1 信息图组件骨架 | 内容关系 → 构图骨架 | **枚举**（带内容门槛） | `components.md` 12 个 |
| L2 图表配方 | 数据类型 → 几何配方 | **枚举**（带安全原则） | `charts.md` 4 类 |
| L3 动效 recipe | 气质 → 入场编排语义 | **枚举**（带禁用清单） | `motion.md` |
| L4 页面版式构图 | 每页的具体布局 | **禁止枚举，原则驱动** | 五条第一性原则 |

分层的关键论证：L0–L3 的枚举对象是**有限集合**（内容关系就那么多、图表数据类型就那么多），枚举它们成本低收益大；L4 的组合空间是**开放的**（骨架 × 主题 × 密度的笛卡尔积），枚举必然挂一漏万，只能用原则。枚举的粒度红线：**到骨架为止，不下沉到页面**。

## 3. 枚举项的法定结构（入库规范）

凡 L0–L3 的枚举项，入库必须七件齐全。缺任何一件不入库——这是枚举可扩展的核心保障，新项的完整度不由作者自觉，由结构强制。

1. **身份卡**：名称、一行气质、适用场景、**与现有项的可区分性声明**（"它和 B1 的区别是什么"答不上来就不该存在——防枚举膨胀的第一道闸）。
2. **token 块**：可机械复制的完整变量块（主题项）或结构骨架（组件/图表/动效项）。token 化是"换肤零风险"的前提。
3. **使用规则**：Do/Don't，量化优先。"高亮色单页最多一个视觉重心"是规则，"高亮要克制"是废话。
4. **密度适配**：该项在 low/high 两档密度下的参数变化（取档、容量、是否禁用）。密度是全局决策，枚举项必须回答自己在两档下的形态。
5. **跨层绑定**：主题项必须给出图表 token 推导（或声明走统一推导规则）；组件/图表项必须给出可编辑分层声明（哪些文字 `data-editable`、哪些 `data-editable-skip`）。
6. **反模式**：该语言下的典型崩坏形态（如 B 系"高亮色泛滥即掉档"、C3"mono 正文的行高陷阱"）。反模式是枚举项里信息量最高的部分——它记录的是"为什么这样设计"，新人/新 AI 加项时才知道红线在哪。
7. **验收标准**：分三级（见 §4），**至少机器可验级必须通过才准入库**。

范本参照：frontend-slides 的 bold-template-pack 是目前所见最完整的枚举写法（每套 design.md 固定七段结构：token frontmatter → 材质叙事 → 密度哲学 → Do/Don't → 编号不变量 → 已知缺陷 → CJK 专节，见 `projects/frontend-slides.md`）；codex 风格库的量化验收（"标题页 1 主视觉 + 2-4 标签，禁 5+ 模块"）是验收标准写得最硬的样本（见 `projects/codex-ppt-skill-main.md`）。两者合并即本规范。

## 4. 验收标准三级体系

| 级别 | 手段 | 例子 | 强制性 |
|---|---|---|---|
| 机器可验 | 静态脚本（grep/解析） | token 块在场且变量名合规；无主题外 hex；组件标记（editable/skip）完整 | **入库必须通过** |
| 渲染可验 | Playwright 测量 | 无溢出 px；正文字号 ≥ 档位下限；accent 色块面积 ≤ 阈值；对比度达标 | 入库必须通过（主题项至少跑一个样板页） |
| 人工可验 | 清单式 checklist | 气质与身份卡一致；反模式未出现；两档密度下都成立 | 入库时人工过一遍，留记录 |

验收标准本身也要克制：**只收录"违反即丑"的不变量，不收录风格偏好**。验收项一旦多过十条，要么是枚举项设计得不够自洽，要么是把原则层的东西误塞进了枚举。

## 5. 可扩展性保障（新增枚举项流程）

1. 提出身份卡，先过可区分性论证（与现有全部项两两比对）；
2. 按 §3 七件写全，缺失项标 TODO 不入库；
3. 跑机器可验 + 渲染可验；人工 checklist 过一遍；
4. 入库并更新选择建议表（themes.md 的"选择建议"、components.md 的"内容关系速查"）；
5. 若新增项属于现有枚举项的微调变体（只差一个色值/一个参数），**优先参数化推导而非新增枚举**——themes.md 的图表 token 统一推导（`color-mix` 从 accent/ink/paper 派生系列色）就是这个原则的范例：13 套主题没有枚举 13 套图表色，一条推导规则全覆盖。

## 6. 现状对照与演进路线

`themes.md` 13 套主题目前具备七件中的第 1、2 件和第 3 件的一部分（使用要点 + 禁忌），缺第 4（密度适配）、5 的显式声明（图表推导已有统一规则，达标）、6（反模式只有 B 系有一句）、7（无验收标准）。`components.md` 12 个组件具备 1、2、3、5，缺 4、6、7。

演进纪律（避免一次性大改的冲动）：

- **新增项必须全规格**——七件不齐不入库，从现在起执行；
- **存量项不追溯重写**，按使用频率逐步补验收标准，补一个是一个；
- `scripts/sync-themes.mjs` 单源同步机制不变——枚举结构升级时，同步脚本要先适配（v1.3 的教训：主题结构变更，同步机制必须先行）。
